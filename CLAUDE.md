# Video Transcoder

Serverless GPU video transcoding service. Receives jobs from Video Hub, transcodes with FFmpeg, uploads HLS segments to R2, callbacks to Video Hub on completion.

## Architecture

- `core/` — provider-agnostic: FFmpeg logic, R2 upload, callback, FastAPI app
- `wrappers/` — RunPod is the first processing adapter, Modal the staged second candidate, Docker the development-only v1 adapter; RunPod has two endpoints, so two files: the transcode (`runpod_handler.py`) and the Google Drive import (`runpod_import_handler.py`)
- Stateless — no database, all job tracking lives in Video Hub's Postgres

## Running Locally

```bash
pip install -r requirements.txt
VH_DEVELOPMENT_ADAPTER=1 FFMPEG_ENCODER=libx264 FFMPEG_PRESET=medium WEBHOOK_SECRET=test python wrappers/docker_server.py
```

## Running Tests

```bash
pip install -r requirements-dev.txt   # today only `-r requirements.txt`, which holds pytest and the jsonschema pin
pytest tests/ -v
```

## Contract v2 (draft)

`tests/contracts/transcode/v2/` is a byte-identical copy of the Hub's canonical tree (`laravel/resources/contracts/transcode/v2/` in Video Hub): schemas, limits, reason codes, the paired fixture catalog and signing vectors. Its `README.md` is the normative rule text. Since amendment C1b (2026-10-10) the claim grant (`transcode.claim.granted`) carries the generation's media key in `media_key` for an encrypted dispatch, the one way a runtime receives a key (README section 15), and the dispatch names each storage location by `location_id` with its `bucket` and `credential_ref`, the name of the access profile (endpoint and credentials) this worker's configuration must hold (README section 7, "Reaching a location"). Amendment C1c (2026-10-15) adds rules this worker must meet before the Hub dispatches contract v2: the start's deadline (no storage write after it, a write still open closed within `limits.json` `storage_call_margin_seconds`, and a terminal message built before it returned unchanged), the manifest at `generation-manifest.json` and the stored result at `result.json` under the granted prefix, the unclaimed cause `expired`, and a refused dispatch ending the provider job as failed (README sections 9.4, 11, 12 and 15.1 rules 6 to 9); on the Hub's side, the claim replay record (`claim_replayed`), one key per dispatch and the revoked bootstrap (15.2). The Python validator and the v2 exact-bytes signing live in `core/protocol/` (moved there from `tests/contract/` in D1, 2026-10-10; `jsonschema` is pinned in `requirements.txt`), and the RunPod image ships the tree at the same relative path, `tests/contracts/transcode/v2/` (`Dockerfile.runpod`; `.dockerignore` lets only that directory of `tests/` into the build context, and `Dockerfile.runpod.dockerignore`, which BuildKit reads in its place for that Dockerfile, is the same with the Drive import's files kept out, line for line, as `tests/test_runtime_scope.py` holds). `core/protocol/files.py` `verify_contract_tree()` is the fail-closed start-up check: it raises `ContractTreeInvalid` unless `sha256(SHA256SUMS)` equals `EXPECTED_CONTRACT_DIGEST` and the tree holds exactly the files `SHA256SUMS` lists, each with its listed SHA-256, and nothing but real directories and regular files (a symbolic link, a FIFO or a name that is not UTF-8 refuses it). `core/protocol/settings.py` `WorkerSettings.from_env()` reads the worker's v2 configuration (the `VH_*` variables its docstring lists: accepted versions, audience, the keys of both directions, the claim and callback URLs, the clock skew and one storage profile per `credential_ref`) and refuses it unless whole (`SettingsInvalid` names the variable and the rule, never the value; no repr shows a key or a secret). `core/protocol/messages.py` builds what the worker sends (`claim`, `progress`, `result_completed`, `result_failed`, `unclaimed`: pure, keyword-only, typed identities, each value and each finished message checked against the contract's schema definitions), `encode()`s it compactly within its kind's byte limit, `seal()`s it, and builds the contexts it validates with (`worker_sender_context()`, `receiver_context()`, both through `TrustedContext.from_dict()`, the only constructor; a context and its `expect` are immutable). One start of the worker for one dispatch is `core/protocol/handler.py` `handle()` (README section 15.1): `dispatch.py` `accept_dispatch()` takes the RunPod job input (`{vh_message, vh_signature}`) and accepts it only when the carrier has its shape, the exact message bytes verify under a Hub-to-worker key before anything is parsed, the message is an accepted `transcode.request` for this worker and its `key_id` names a key that verified it (`inbound.py` `accept_signed()`, used for the claim grant too); a refused dispatch raises `DispatchRefused`, which names the step, the layer and the reason, never content. `claim.py` `claim_execution()` then claims with a fresh random `runtime_id` kept in memory: it works only on a `200` whose body verifies and is an accepted `transcode.claim.granted` for this dispatch, runtime and encryption (the returned `Grant` holds the media key, never shown by a repr); it claims again only after a transport failure or a retryable `hub.error`, never at or after the dispatch's `claim.expires_at`, for at most `CLAIM_PATIENCE_S` (120 s: a billed runtime does not wait out the bootstrap) and never at or after the end of the start's wall time (below), both measured on a monotonic clock, and every other ending is `Unclaimed` with the contract's cause: `refused` with the Hub's code, `unreachable` when the Hub never answered (a gateway's 502, 503 or 504 without a `hub.error` counts as no answer and is claimed again, which is safe because the Hub gives one runtime the same grant again), or `invalid_answer` for any other answer, a redirect included. `transport.py` is the HTTP carrier, written on sockets with a strict reader of its own, no HTTP library (one POST, https only: no redirect, the certificate and host name verified against `certifi`'s bundle, nothing read from the environment, the whole exchange held to one deadline (the host's addresses share it for the TCP connect, and from the TLS handshake on a watchdog shuts the socket when it passes, so a trickling answer is cut like a hanging one; only name resolution cannot be cut short), the answer's head and body cut at their size limits and never decoded, and an answer that is not whole and plain (a head or body cut short, a body delimited by nothing or in two ways, an interim answer, any line outside the small HTTP/1.x grammar it reads) treated as no answer); `outbox.py` `seal_message()` is the one way a built message becomes signed bytes (encoded, validated by the worker's own validator under the sender context, then signed), `runpod_output()` the job output carrier and `deliver()` the best-effort POST to the callback address, the same bytes both ways (sent again, as a claim is, after a transport failure, a retryable `hub.error`, or a gateway's 502, 503 or 504 without a `hub.error`; any other answer that is not a 2xx ends it). One start has one wall-time budget: `handle()` reads the monotonic clock before anything else, and that reading plus the dispatch's `limits.max_wall_time_ms` is the instant the claiming ends by, the job runner's deadline is counted to, and after which no callback attempt starts (the job output carries the same bytes). No claim body, grant body, key or bootstrap token is ever logged, put in an error or returned as job output. `handler.py` `load_runtime()` checks the contract tree and reads the settings once per process, before any job. The job runner `handle()` hands a claimed execution to is `core/job/` (next section). The image's entry point is `wrappers/runpod_handler.py`, v2 only since D1's last slice: run as the program it calls `main()` and nothing else, which sets up the log, builds the handler and starts the SDK's serverless loop with it (a test hands `main()` a starter of its own in the SDK's place); `build_handler(os.environ)` checks the tree, reads the whole configuration and then removes the scratch directories a killed process left (`remove_leftover_scratch()`, next section), all before any job is taken, and each job of the RunPod SDK is one `handle()` with the job runner. Only two errors leave the handler, both the wrapper's own and without a cause or a context, because the provider records a failed job's error text and whole traceback: `JobRefused` with the refusal's own words for a dispatch the worker may not act on, `WorkerFault` naming only the class for a bug (logged once by class and stack, and only after the `except` block that caught the bug has ended: when a log handler fails on a line, Python's logging prints a report of its own to standard error with every error that failure is chained to, which inside the block would be the bug with its own text). Once a storage request was abandoned in this process, at the deadline or at its own ceiling (`core/job/storage.py` `abandoned_requests()`, counted wherever it happens: in a job that then completed, and between two jobs), every job's output also carries `refresh_worker: True`: the SDK takes that member out and has the pod stopped, so an abandoned request's thread and connection end with the process instead of piling up in a warm worker, and the Hub still reads exactly the carrier. The entry point configures logging only when it is run as the program, first thing in `main()`: before the SDK is imported, whose import hangs a handler of its own on a root logger that has none, and before the handler is built (`configure_logging()`: the worker's lines at INFO, and nothing at all from urllib3, the HTTP library under the storage clients, whose own warnings name the storage host and a request's whole URL, so the bucket and the object key too; its whole family of loggers is cut off at its parent, because the library has moved a warning between loggers from one version to another and the SDK's import resets that parent's level); importing the module configures nothing. `tests/test_runtime_scope.py` keeps the two worlds apart: the RunPod entry point reaches `core.protocol` and `core.job` and none of the v1 modules, and `core.api`, the Modal app and the v1 dev server never import `core.protocol`. An image built from this commit serves only a Hub that dispatches contract v2: the Hub's live dispatch is still v1 (below) until its own processing slice lands, so the two are released together. The tests stay in `tests/contract/`: `pytest tests/contract` checks the copy against `SHA256SUMS`, runs the start-up check against tampered copies, every fixture and the signing vectors. Never edit the copy by hand: copy the Hub tree, and any change moves `EXPECTED_CONTRACT_DIGEST` (`core/protocol/files.py`) and the Hub's `ContractFiles::EXPECTED_DIGEST` together.

## The job runner (D1 of the Hub's issue #51; called by the RunPod entry point)

`core/job/runner.py` `JobRunner.run(claimed, runtime)` runs one claimed execution to its one ending and returns it sealed: `transcode.result.completed` once the generation and its manifest are stored under the granted prefix, `transcode.result.failed` for every other ending, with the typed failure and the contract stage it ended in (null before the first). Before anything is read it takes what is left of the start's wall time as its deadline (the limit counts from the moment `handle()` began, so the claim has already spent some of it; with none left the execution ends at once as a retryable `deadline_exceeded/wall_time_spent_before_start`: nothing was done), resolves both access profiles (`credential_ref` of the source and of the output; an unknown one is `configuration_error/unknown_credential_ref`), requires the dispatch's media profile to be one the worker holds (`core/profile.py` `supported_profile(id, version, sha256)`: id, version and `profile_digest()`, the SHA-256 of the profile's canonical JSON, pinned for the pilot profile by `tests/preflight/test_profile_digest.py`; a changed profile is a new revision, and the Hub must send its digest), checks that the grant's key fits the dispatch's encryption, names the encoder (the image digest of `VH_IMAGE_DIGEST`, the installed ffmpeg's version from `core/job/ffmpeg_version.py`: a missing or broken installation is `configuration_error/ffmpeg_unavailable`, a start that failed for want of a resource is a retryable `resource_exhausted/ffmpeg_version_start_failed`, a run that passed the check's own limit or ended on a signal a retryable `internal_error/ffmpeg_version_run_failed`, and a check the execution's deadline ran out on a retryable `deadline_exceeded/ffmpeg_version_deadline_exceeded`: the start's time went to its claim or to this check, and nothing was read or encoded yet), and makes both storage clients (a factory that raises a `MemoryError` or an `OSError` other than a missing or unreadable file, as when no memory or descriptor is left, is a retryable `resource_exhausted/storage_client_start_failed`; any other failing factory is `configuration_error/storage_client_unavailable`; both name the side and the error's class, a shortage its errno's name too, never its text). Then the stages: `probing` (the preflight, and the plan: the renditions and the room they and the package may take, so a source that cannot be planned or does not fit fails before it is downloaded), `downloading` (`core/job/storage.py` `download_source()`: the whole source through the same ranged reads as the preflight, each conditional on the recorded ETag, into the execution's own scratch directory; an `OSError` while that directory is made or locked is typed, never a bug and never final: `resource_exhausted/scratch_full` for a full disk, any other a retryable `resource_exhausted/scratch_create_failed` that names the errno by its symbolic name and nothing else of the error, a `FileNotFoundError` and a `PermissionError` included, because the process start already refuses a scratch root that is missing or that it may not write to, so such an error here is this one worker's trouble after its start; a close of that file that fails after the whole copy is a failed write, `scratch_full` or `source_write_failed`), `transcoding` (the planned renditions one at a time, each within what the earlier ones left, with the grant's media key), `finalizing` (thumbnail, master playlist, manifest, the manifest validated by the worker's own validator, and the completed result built and self-checked once with what is known then, both before anything is uploaded: a result the validator would refuse is `internal_error/result_self_check_failed` at `finalizing` with nothing stored, and the result that is returned is built anew after the upload, with its own message id and send time) and `uploading` (`upload_generation()`: exactly the files the manifest lists, each as `<granted prefix>/<relative path>` in the dispatch's output bucket, then the manifest last, as the completion marker; a bucket that is no contract bucket, a prefix that is no contract object key, a path that is no contract `rel_path`, a file reached through a link, or artifacts that are not as many, or not of the total size, the manifest records are refused before any request; nothing is listed, read back or deleted). Every request of the storage is held to the execution's deadline while it is in flight, and to a ceiling of its own (30 seconds plus one second per 256 KiB of its size): the client's read time-out bounds a silence only, so each request runs on a helper thread the job stops waiting for at the nearer of the two (`storage._within`; `DeadlineSource` gives up the preflight's reads in the same way). A request that outlasts its ceiling while the deadline still has time left is a failed attempt that passes (`source_unavailable/source_read_stalled`, `output_write_failed/upload_stalled`, both retryable) and is made again (a read of the preflight is not: the execution then ends retryable at `probing`), so one trickling request cannot eat the wall time. A request that ends after the deadline does not count, however soon after, so a manifest stored late never yields a completed result, and the job closes an abandoned upload's file itself, so that request gets no more of it and its disk space is freed. The bytes the client reads of each file are counted and hashed against the manifest's size and SHA-256 (what it reads is what it sends, unless the storage answered before the body, when the client drops what it reads and the storage's answer alone decides): the client reads a body through to sign it before it sends it, so a file that changed before its upload is refused before a byte of it is sent, and one that changes between the two passes is refused at the end of the second, when its bytes went out under a signature that no longer fits them. A file is opened without waiting, so a FIFO put where it was is refused at once, and a file that fails under the client's read (an error of the disk) ends the upload as `internal_error/artifact_changed_before_upload` too, named by its relative path and the errno's name, and is not sent again. A refusal the storage would only repeat (an answer with a status from 300 to 499 but the passing ones: 302, 307, 408, 409, 429 and a few error codes; an `AccessDenied` is the typical final one) is `output_write_failed/upload_refused`, not retryable and not sent again, so that an encode is not repeated for a write that is never allowed; any other failed request is made again only after a wait (0.5 and 2 seconds for a read of the download, 0.5, 2 and 8 seconds for a PUT, each times a factor drawn between 0.5 and 1; a PUT's `Retry-After` is honoured up to 30 seconds; no wait is made that would not end before the deadline) and ends, when its attempts are used up or the next wait would not fit, as the last attempt's own retryable failure (`upload_failed` or `upload_stalled` for a PUT, the source's own failure for a read). A stage that runs out of time is final (`deadline_exceeded`; the one exception is a preflight whose own budget ran out on a slow storage, `source_unavailable/probe_source_slow`, in the next section), and its result's detail ends with how many seconds of the start's wall time were gone before the execution began, so that a limit that is too small can be told from a start whose claim took the time (where a stage's own budget ran out with wall time left, the code names that budget and the numbers only show that the wall time was not what ran out; a detail with no room for the numbers goes without them, and so does an execution whose reading of the time left lay too far back to be counted). The output side has its own S3 client (`upload_client()`: a checksum only where an operation requires one, so a PutObject is one plain signed PUT; `boto3>=1.36`). Neither client follows a region redirect (`core/source_reader.py` `without_region_redirects()`, applied where each is made, stops botocore's region redirector through its public events: one call is one request, never one sent again signed for a region the storage's answer names nor a HeadBucket of the client's own, and a redirect answer comes back as the storage's own error; tests through the real client pin it against a botocore that changes). The media key goes to the encode and nowhere else, and the grant lets go of it (`core/protocol/claim.py` `Grant.drop_media_key()`) as soon as the transcoding stage ends, however it ends, and in any case before `run()` returns (README 15.1, rule 4); the storage credentials go to the two client factories and nowhere else, and the clients an execution made are closed before `run()` returns, best effort, unless the process has abandoned a storage request, which may still be using one. A result's `source.bytes_read` is the larger of what the preflight read and what the download wrote, never their sum, and a failed `source_integrity_mismatch/source_changed` result carries no `source` block: it claims no observation of an object that was no longer the recorded one. A storage failure shows a class name and an error code (kept only when it is wholly of `[A-Za-z0-9.]{1,64}`), a typed failure raised in place of a caught error (the storage client's, the operating system's) carries that error neither as its cause nor as its context, in the storage module and the source reader as in the stages (`core/probe.py`, `core/encode.py`, `core/hls_key.py`, `core/package.py`, `core/thumbnail.py`), where the line that tells of a caught error is likewise written only once its `except` block has ended (one line cannot leave its block, the preflight loopback server's `handle_error`, which the standard library calls from inside its own: it holds nothing of the error but its class name), and a bug is logged by its class and stack only, never with the error's own text. `core/job/progress.py` sends `transcode.progress` best effort (each message self-checked, one POST with a 3-second time-out, `event_seq` strictly increasing) and stops for the rest of the job after three messages in a row that were not delivered, or once its posts have taken 30 seconds together: a report is posted on the job's own thread, so progress costs an execution at most those 30 seconds plus the one post in flight (3 seconds; longer only while a name resolves, which no time-out cuts short), however slowly the Hub answers. `core/job/config.py` `JobSettings.from_env()` reads `VH_IMAGE_DIGEST` (required, `sha256:` and 64 hex digits) and `VH_SCRATCH_DIR` (optional; the absolute path of an existing directory the process may write to and search, of printable ASCII only, without `:`, `%`, a double quote or a backslash, refused otherwise at process start; the default is the system's temporary directory, and a usable system temporary directory (`TMPDIR`) is required whatever the scratch directory is). The scratch directory is removed whatever the ending, and the execution holds an exclusive advisory lock (`flock`) on it from right after it is made until after it is removed, which the kernel releases when the process dies. The scratch root must therefore be on a file system on which a directory can be locked with `flock`, and the process start checks it (`JobSettings.from_env()` through `lock_refused_in()`: one directory made, locked and removed; a root that refuses the lock is refused, and where the directory cannot be made the start goes on and a job meets that as its own retryable failure). One host's kernel keeps the lock, so it tells a live directory from a leftover only between processes of one host, which is why the removal looks only at this host's directories: on a root shared between hosts no worker removes what another host made, running or left behind, so those leftovers (and this host's from before a reboot) stay until an operator removes them. Keep the scratch root on the worker's own disk: a remote file system that two workers of one host each mount for themselves keeps their locks apart, which no check sees. `core/job/scratch.py` `remove_leftover_scratch(scratch_root)` removes what a killed process left and returns how many (the entry point's `build_handler()` calls it at process start, once the configuration was read and before the handler is returned): of the scratch root's direct children whose name starts with this host's prefix (`scratch_prefix()`: `vh-job-`, then a tag of the host's running kernel, taken from its boot id, or from its node name where there is no boot id) it removes the real directories this process's user owns whose own modification time is at least 60 seconds old and whose lock nobody holds, follows and removes no symbolic link, lets no error of the root or of a directory out (what a log line that cannot be written raises is dropped by the entry point), and logs the count and an error's class, never a path; a directory another host made, one this host made before its last reboot and one of an earlier image (`vh-job-<random>`, no tag) are never touched (that is so where the tag comes from a boot id, on every Linux host and so in the image; a tag taken from the node name, as on the development host, survives a reboot and is shared by hosts of one node name). Tests: `tests/job/` (the runner's own decisions with the stages replaced by fakes; the leftover removal and the lock against real directories; storage against a fake S3 client and, for the request's shape, the real client, which opens no connection; an end-to-end run with the real ffmpeg, skipped without it).

## Preflight (B08 core, D3 of the Hub's issue #51; called by the job runner)

`core/probe.py` `run_preflight()` establishes a source's media facts without downloading it and decides its admission against a versioned media profile (`core/profile.py`, `PILOT_PROFILE`) and the dispatch's own limits (the smaller limit wins). It reads the source through `core/source_reader.py`: exact byte ranges, each conditional on the recorded ETag, with a byte, request and time budget the reader enforces itself; a storage that ignores the range or the condition fails closed. ffprobe reads only a loopback URL this process serves from that budgeted reader, with a cleared environment, `-protocol_whitelist http,tcp` and the profile's demuxer whitelist, so a playlist or any other format that opens further URLs is refused before it opens one. Every subprocess runs under `core/bounded_process.py` (a deadline that only shortens, the whole process group killed, capped output). Failures are typed with the contract v2 error classes (`core/failure.py`); facts come from `core/source_facts.py` and the decision from `core/admission.py`. A preflight that runs out of its own time budget (the profile's probe wall time, 60 seconds for the pilot) fails for good as `deadline_exceeded/probe_deadline_exceeded`, with one exception (`core/probe.py` `_out_of_time`): while the execution's own deadline still has time left, reads of the source that took at least half of the time the preflight had used (`PROBE_SOURCE_SLOW_SHARE`; the budgeted reader measures it, a read still in flight included, `BudgetedSource.read_time()`) mean the storage was the slow party, and the failure is the retryable `source_unavailable/probe_source_slow`: another start may meet a faster storage, where media that takes too long to probe would take as long again. Either of the two endings logs one warning with the two measured numbers (seconds in reads, seconds elapsed), the final one also with what made it final (the execution's own deadline had passed, or the storage was not the slow party), and nothing of the source. ffprobe's own I/O time-out (`-rw_timeout`) is 5 seconds longer than what that budget leaves (`PROBER_IO_TIMEOUT_MARGIN_S`), so the worker's kill at the deadline always comes first: an ffprobe that gave up a read by itself would exit with an error, which is typed as the media's fault. The facts are what the container and the probe window declare (the largest declared duration counts; a rotation only from the container's exact display matrix), so the encode stage that follows must re-enforce the admitted bounds on the decoded stream: cut the output at the admitted duration, bound the frame rate and the decoded pixels, and run with autorotation off, applying exactly the admitted rotation (an orientation carried only in the coded stream is ignored by contract). The job runner (`core/job/runner.py`) runs it as its first stage, before the full download. Tests: `tests/preflight/`, with media fixtures generated by the local ffmpeg (skipped without it).

## Encode stage (B08 core, D3 of the Hub's issue #51; called by the job runner)

`core/encode.py` `encode_rendition()` turns the downloaded, admitted source into one HLS rendition and holds the encode to what the preflight admitted, whatever the decoded stream turns out to be. `core/renditions.py` plans the renditions: each is named by the short edge of its display frame (portrait included), never upscaled (when every requested rung is above the source, the smallest is encoded at the source's own size), constant-rate at the declared frame rate held between the profile's floor (1 fps, so every segment has a keyframe) and ceiling, with the smallest H.264 level whose limits hold. `core/encode_command.py` builds the command: the input readable only as a local file through the one demuxer the preflight saw, the output writable only to local files, a cleared environment; only the codec's crop applied (the container's crop is not in the preflight's geometry); the output cut at the admitted duration (plus a frame-count belt); the `fps` filter bounding the output frame rate; `-max_pixels` bounding the decoded frame (the profile's cap plus the slack libavcodec's buffer alignment needs); autorotation off and exactly the admitted quarter turn applied; only the admitted streams mapped and no metadata carried over. `core/hls_key.py` holds the AES-128 key for the length of one encode: on Linux in a memory file ffmpeg inherits, so it never touches a disk and disappears with the last process holding it; elsewhere in an owner-only file beside the output. `periodic_rekey` gives every segment its own IV (its media sequence number), written in the playlist; without it ffmpeg (7.1 and 8) encrypts every segment with the first IV. Each rendition has a time budget (the profile's base plus so much per second of admitted media, never past the caller's deadline) covering the run and the verification: no count of packets or frames bounds what a decoder does (an AV1 temporal unit or a VP9 superframe carries many frames), so time is the decoder's bound, and the one the provider bills. While ffmpeg runs, a monitor in `core/encode.py`, called through `core/bounded_process.py`'s monitor hook, stops it when the output passes its byte or file allowance (the smaller of the dispatch's output limit and the scratch ceiling less the source). The decoder's refusals of an oversized or invalid frame (libavutil's two size checks, libdav1d's limit) are recognized anywhere in its stderr, not only in the kept tail. ffmpeg can exit 0 without writing a segment, so the output is always verified afterwards: the exact playlist grammar (`core/hls_playlist.py`); every file accounted for, the exact limits, the cut held, and every segment proven whole MPEG-TS (decrypted and its padding checked when encrypted) whose video PTS span matches its EXTINF and whose count of video frames matches that span, in the pass that hashes it (`core/encode.py`); then ffmpeg decodes the whole rendition once through a private copy of its playlist (`-xerror -err_detect explode`), and its decoded frames must equal the frames counted; less than 1 MiB of disk left after the run, or behind a failure, is a retryable `scratch_full`. Known gaps, both advisory (a write failure cannot practically produce them: on the image's ffmpeg 7.1.4, plain segments are written in 256 KiB writes and encrypted ones in 32 KiB writes, and ffmpeg writes nothing after a failed write; re-measure on an ffmpeg upgrade): whole audio packets lost after a segment's last video frame decode clean, so no check sees them (a strict xfail test records it); and on ffmpeg 8.0.1 (arm64) some cuts inside the very last frame decode clean, which 7.1.4 refuses. The job runner encodes the renditions of a job one at a time on a shared scratch disk: a failed sibling's removal could otherwise free the space the free-disk check relies on. The bandwidth is measured from the segments on disk (RFC 8216 4.3.4.2). Tests: `tests/encode/` (the memory-key tests run only on Linux: run the suite in the worker image too).

## Thumbnail, master playlist and manifest (B08 core, D3 of the Hub's issue #51; called by the job runner)

`core/thumbnail.py` `make_thumbnail()` writes the optional `thumbnail.jpg`: the picture on screen a tenth into the admitted duration but never later than 5 s (the `fps` filter first, as the renditions have it, and the seek snapped down onto that frame grid, so a still image or a slide show still shows its picture), read through the rendition's own input arguments (`core/encode_command.py` `input_arguments`) and sought on the output side (ffmpeg decodes from the start rather than trust the container's seek index), turned by exactly the admitted rotation, scaled to the largest rendition's aspect at the profile's short edge (never upscaled) and written as a baseline 4:2:0 JPEG holding nothing but its image (an ICC profile travels as frame side data, so the filter chain deletes it; `+bitexact` keeps the encoder's comment out), within its own byte limit and time budget (`EncodeProfile.thumbnail_*`); the file is verified (a regular file within the limit, a whole JPEG whose frame header names the planned size and with no segment before its scan but a JFIF header, its tables and its frame: any metadata segment is refused) before it becomes an artifact. It is optional: every other ending is a `thumbnail_unavailable` diagnostic (`core/failure.py` `Diagnostic`) with no file left, and only the caller's deadline and a full scratch disk fail the job. `core/package.py` writes the master playlist (`#EXTM3U`, version 3, independent segments, then for each rendition in planned order a `STREAM-INF` with the measured `BANDWIDTH` and `AVERAGE-BANDWIDTH`, `RESOLUTION`, `FRAME-RATE` to three decimals and `CODECS`, followed by its playlist path) and, last, the contract v2 `generation.manifest`: compact JSON in the schema's key order listing the master, the thumbnail and every rendition's playlist and segments with size and SHA-256; the manifest is never an artifact itself, and its preconditions fail only on a wiring bug. Both files are created new (`O_EXCL`, `O_NOFOLLOW`); a failed write removes the partial file and is typed (`scratch_full` or `package_write_failed`). The job calls `reserve_package()` right after `OutputAllowance.for_job()`: it sets aside the master's 4 KiB, the thumbnail's `thumbnail_max_bytes`, the manifest's `manifest_max_bytes(max_artifacts)` and two files, and gives the renditions the rest. The job runner calls these in its `finalizing` stage and then validates the manifest with the contract validator (`worker_sender`, channel `storage`) before anything is uploaded. Tests: `tests/encode/test_thumbnail.py`, `test_package.py` (the manifest passes the contract validator, its worst case included) and `test_package_end_to_end.py`.

## The Google Drive import job (Hub issue #50 item 3b)

A second RunPod endpoint, of its own image, imports one Google Drive file into the multipart upload the Hub opened: the worker holds no storage credential, only the presigned URLs of that one upload and of one receipt that the job's input carries (the Hub's import design, G-2). `core/drive_import/job.py` `run_import(input_document, settings, http, clock)` is one job, everything outside it a parameter (the session is `core/drive_import/transport.py`'s `HttpSession`: `get(url, headers, timeout, stream, stop_line=…)` and `put(url, data, headers, timeout, stop_line=…)`; the clock gives `now()`, `monotonic()` and `sleep()`). In order: the input against `input.schema.json`; then the settings (all three, or `not_configured` before any request); then the input's MAC (`core/drive_import/contract.py` `input_mac_verifies()`, README section 3.1: HMAC-SHA256 under the import key, which is the receipt key, of `import/v1 input` and a line feed followed by the canonical form of the input without its `mac`, compared in constant time), so that the worker acts only on an input the Hub wrote, member for member (another file id or other checksums beside a real job's URLs do not verify); then the input's rules beyond its schema (`core/drive_import/input_check.py` `check()`: every URL `https://{IMPORT_STORAGE_HOST}/{bucket}/original-videos/{uuid}/…` with no user information, port, bracket or other host, one bucket and one video throughout, the parts `original.{ext}?…` with their own `partNumber` and one `uploadId`, the receipt `import-receipt-{job}.json?…` with none, the plan the size's own, an integer member written `15.0` read as the integer, the deadline not passed; a refusal carries no other error as its cause or context); any refusal of the input is `input_refused`. Then Google's metadata of the file once more (`core/drive_import/google.py`; the host `www.googleapis.com` and the paths fixed in code, the file id from the input alone, the key in `X-Goog-Api-Key`, the link's resource key in `X-Goog-Drive-Resource-Keys`, `Accept-Encoding: identity` on both of Google's requests, a 200 or a 206 in a content coding refused as `download_failed`, and the error document of an answer in one never read, since the HTTP library would decode it whole before the 64 KiB limit counts it: a 400 or a 403 in a content coding is `provider_refused`): in the trash is `file_removed`, `canDownload` present and not true `link_not_shared`, and another size, or another MD5, SHA-1, SHA-256 or head revision where the input carries one (a value Google gives now that the input did not carry is not compared), `source_changed_at_provider`, all before any write (G-10). Then the download (`alt=media`; a 200, or for a resumed request a 206 whose `Content-Range` starts where it was asked; any other shape is `download_failed`), its bytes counted against the expected size (the chunk that goes past it ends the job `size_exceeded` at once, fewer at the end is `size_short`) and hashed; a reset or a time-out resumes with `Range: bytes={first byte of the part in flight}-`, at most three requests for each part (the one that reached it included, after waits of 0.5 and 2 seconds), then `download_failed`. Each part of 64 MiB, buffered whole, is PUT to its URL as soon as it is whole (`core/drive_import/store.py`: `Content-Length` and `Content-MD5`, connect 10 s, a read time-out of one second per MiB of the body, at least 60 s (64 s for a whole part), made again after 0.5, 2 and 8 seconds on a 5xx, a 408, a 429, a time-out or a connection error, so at most four requests; any other answer but a 200, a redirect included, is `upload_failed` at once; a 200 must carry the store's ETag in the receipt's form, one pair of quotes taken off, else `upload_failed`; the answer's body is never read); the last part only once the whole stream matched Google's SHA-256 when the input carries one, else its MD5, else nothing (`checksum_verified`: `sha256`, `md5` or `none`; a mismatch is `integrity_failed` and the last part is never written). The download, the PUTs and the hashing run in series, one part at a time, so a job's time is the download's plus the uploads' plus the hashing's: the rate the Hub's writer deadline assumes (`transferSeconds()`) must be measured on a whole job, Google to the store, not on a download alone. Then the receipt `{contract, job, bytes, checksum_verified, parts: [{n, etag}], mac}`, its MAC under the receipt key (`contract.receipt_mac()`, README section 5.1, no prefix), checked against `receipt.schema.json` and PUT to the receipt URL as JSON with the same tries (a failure is `upload_failed`). The output is `{contract: "import/v1", status: "imported", code: null}` or `{…, status: "failed", code}`, checked against `output.schema.json` before it is returned; the Hub reads only its code, the import's result comes from the store and the receipt. Google's answers map as the Hub's own client maps them (`HttpGoogleDriveFiles`), with one addition of the worker's own: a 404 is `file_removed`, a 429 or a 403 with a quota or rate reason `provider_quota`, a 400 or a 403 that is the key's fault (its reason or an ErrorInfo reason) `not_configured`, a 400 or a 403 whose reason says the file is not there for the link (`notFound`, `insufficientFilePermissions`, `cannotDownloadFile`, `teamDriveMembershipRequired`: `google.NOT_SHARED_REASONS`, a list the Hub's client has not, answering these as `provider_refused`) `link_not_shared`, any other 400 or 403 (`cannotDownloadAbusiveFile` among them) `provider_refused`, a 408, a 5xx, a time-out or a connection error a try made again, any other status, a redirect included, `download_failed`. The real session (`transport.RequestsSession`) is a `requests.Session` with `trust_env=False` (no proxy, netrc or other certificate bundle from the environment) that follows no redirect and reads none's body (`allow_redirects=False` on every call, and a session whose `get_redirect_target()` names none: requests otherwise reads the body of a 3xx it does not follow), and sends each PUT with `stream=True`. The stop line is `writes_end_at` − 120 s, held on the monotonic clock (`core/drive_import/clock.py` `StopLine`): no request starts and no wait begins once it has passed (`deadline`); every request's time-outs are cut to what is left of it; a PUT's body (`transport.BoundedBody`, a file-like body urllib3 sends in blocks of 16 KiB, where `bytes` would go in one `sendall` that the socket's time-out bounds as a whole) stops giving bytes when it passes; and every request carries it to the session, whose watchdog holds the request to it: the session's connections (a connection class of the module's own, kept by its adapter's pools) give the watchdog the socket that carries each of them, held weakly for as long as it lives (the TCP socket of an HTTP connection, the TLS socket of an HTTPS one once its handshake is done), so that the watchdog still reaches a socket http.client handed over to an answer that ends the connection (`Connection: close`, HTTP/1.0, a body framed by the close), and, between an HTTPS connection's TCP connect and the end of its handshake, a duplicate of the TCP socket's descriptor, which the TLS socket takes over meanwhile (closed once the TLS socket is kept). A timer armed just after the stop line latches the session's expiry, under the lock that keeps those sockets, and shuts each of them (the base class's `socket.shutdown()`, never the TLS socket's own, which lets go of its TLS state first). So a TLS handshake whose server never answers, a download that trickles, a metadata answer that trickles and a PUT whose answer never comes all end at the stop line, framed by a length or by the close; and once the latch is set a socket kept later is shut as it is kept, a connection goes no further after its TCP connect and after its TLS handshake, and the session starts no request (each raises `DeadlineReached`, which the job answers as `deadline`). A connection also connects within the stop line: it resolves the host's name once and tries each address only while the session has not expired, with the connect time-out cut to what is left of the stop line, so that several addresses share that time. The job, finding the stop line passed, answers `deadline` (a try that fails after the stop line, its tries used up or its stream ended, is the stop line's, never `download_failed`, `upload_failed` or `size_short`). What nothing cuts short is the name resolution itself, which no time-out of the HTTP library bounds and which has no socket to shut; it ends where the latch is read next. No byte is written after the stop line but for the block in flight. The contract copy is `tests/contracts/import/v1/`, a byte-identical copy of the Hub's `laravel/resources/contracts/import/v1/` (marked `-text` by `.gitattributes`, as the transcode tree), separate from transcode v2; `core/drive_import/contract.py` pins `EXPECTED_IMPORT_CONTRACT_DIGEST` (the SHA-256 of its `SHA256SUMS`, the Hub's `ImportContractFiles::EXPECTED_DIGEST`; any change to the tree moves both in the same change), checks the tree as `core/protocol/files.py` checks its own (`verify_import_contract_tree()`, fail closed, `ImportContractInvalid`), validates with its own local registry of the three schemas (base URI `https://schemas.video-hub.invalid/import/v1/`, nothing retrieved) and computes both MACs over one canonical form, checked against the tree's two known answers (`fixtures/input-mac-vector.json`, `fixtures/receipt-mac-vector.json`); it imports nothing of `core.protocol`. ## Webhook Contract (v1: the development-only adapter)

The v1 pipeline below is retained only for the development adapter (`wrappers/docker_server.py`, also served directly as `core.api:app`); RunPod speaks contract v2 only and Modal stays staged. `core/v1_admission.py` admits v1 execution only when `VH_DEVELOPMENT_ADAPTER` is exactly `1`: `/transcode` otherwise returns 503 before reading the body, and `_process_transcode` checks again before doing any work. `/health` remains available. The development compose file explicitly opts in; the Docker image starts disabled without the variable.

POST /transcode with JSON body (see core/api.py for schema). Source acquisition uses only the existing S3 object: nonempty `s3_bucket` and `s3_original_path` are required (422 on validation failure). Auth: HMAC-SHA256 over `"{timestamp}.{raw_body}"` with the shared `WEBHOOK_SECRET` — headers `X-Signature: sha256=<hex>` + `X-Timestamp: <epoch>` (5-min tolerance). An empty `WEBHOOK_SECRET` refuses every request with 401 (`core/signing.py` `verify_request()`).

`_process_transcode` returns the result payload (status `ready`|`failed`); callback delivery is attempted but non-fatal.

## Key Conventions (v1)

- Video ID: UUID v4
- Development quality presets live in `core/config.py`
- Encryption: AES-128, key provided as hex in request, written to temp file for FFmpeg
- R2 upload skips .keyinfo and enc.key files (keys served from Video Hub DB)
