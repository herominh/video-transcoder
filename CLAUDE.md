# Video Transcoder

Serverless GPU video transcoding service. Receives jobs from Video Hub, transcodes with FFmpeg, uploads HLS segments to R2, callbacks to Video Hub on completion.

## Architecture

- `core/` — provider-agnostic: FFmpeg logic, R2 upload, callback, FastAPI app
- `wrappers/` — one file per provider (Modal, Docker, RunPod)
- Stateless — no database, all job tracking lives in Video Hub's Postgres

## Running Locally

```bash
pip install -r requirements.txt
FFMPEG_ENCODER=libx264 FFMPEG_PRESET=medium WEBHOOK_SECRET=test python wrappers/docker_server.py
```

## Contract v2 (draft)

`tests/contracts/transcode/v2/` is a byte-identical copy of the Hub's canonical tree (`laravel/resources/contracts/transcode/v2/` in Video Hub): schemas, limits, reason codes, the paired fixture catalog and signing vectors. Its `README.md` is the normative rule text. The test-only Python validator lives in `tests/contract/` (install `requirements-dev.txt` for the pinned `jsonschema`); `pytest tests/contract` checks the copy against `SHA256SUMS`, runs every fixture and the signing vectors. Nothing at run time uses either yet: the live wire format is still v1 (below), and B08 moves the validator into `core/`. Never edit the copy by hand: copy the Hub tree, and any change moves `EXPECTED_CONTRACT_DIGEST` (`tests/contract/files.py`) and the Hub's `ContractFiles::EXPECTED_DIGEST` together.

## Preflight (B08 core, D3 of the Hub's issue #51; not wired yet)

`core/probe.py` `run_preflight()` establishes a source's media facts without downloading it and decides its admission against a versioned media profile (`core/profile.py`, `PILOT_PROFILE`) and the dispatch's own limits (the smaller limit wins). It reads the source through `core/source_reader.py`: exact byte ranges, each conditional on the recorded ETag, with a byte, request and time budget the reader enforces itself; a storage that ignores the range or the condition fails closed. ffprobe reads only a loopback URL this process serves from that budgeted reader, with a cleared environment, `-protocol_whitelist http,tcp` and the profile's demuxer whitelist, so a playlist or any other format that opens further URLs is refused before it opens one. Every subprocess runs under `core/bounded_process.py` (a deadline that only shortens, the whole process group killed, capped output). Failures are typed with the contract v2 error classes (`core/failure.py`); facts come from `core/source_facts.py` and the decision from `core/admission.py`. The facts are what the container and the probe window declare (the largest declared duration counts; a rotation only from the container's exact display matrix), so the encode stage that follows must re-enforce the admitted bounds on the decoded stream: cut the output at the admitted duration, bound the frame rate and the decoded pixels, and run with autorotation off, applying exactly the admitted rotation (an orientation carried only in the coded stream is ignored by contract). Nothing calls it yet: the claim-first job (D1) runs it as its first stage, before the full download. Tests: `tests/preflight/`, with media fixtures generated by the local ffmpeg (skipped without it).

## Encode stage (B08 core, D3 of the Hub's issue #51; not wired yet)

`core/encode.py` `encode_rendition()` turns the downloaded, admitted source into one HLS rendition and holds the encode to what the preflight admitted, whatever the decoded stream turns out to be. `core/renditions.py` plans the renditions: each is named by the short edge of its display frame (portrait included), never upscaled (when every requested rung is above the source, the smallest is encoded at the source's own size), constant-rate at the declared frame rate held between the profile's floor (1 fps, so every segment has a keyframe) and ceiling, with the smallest H.264 level whose limits hold. `core/encode_command.py` builds the command: the input readable only as a local file through the one demuxer the preflight saw, the output writable only to local files, a cleared environment; only the codec's crop applied (the container's crop is not in the preflight's geometry); the output cut at the admitted duration (plus a frame-count belt); the `fps` filter bounding the output frame rate; `-max_pixels` bounding the decoded frame (the profile's cap plus the slack libavcodec's buffer alignment needs); autorotation off and exactly the admitted quarter turn applied; only the admitted streams mapped and no metadata carried over. `core/hls_key.py` holds the AES-128 key for the length of one encode: on Linux in a memory file ffmpeg inherits, so it never touches a disk and disappears with the last process holding it; elsewhere in an owner-only file beside the output. `periodic_rekey` gives every segment its own IV (its media sequence number), written in the playlist; without it ffmpeg (7.1 and 8) encrypts every segment with the first IV. Each rendition has a time budget (the profile's base plus so much per second of admitted media, never past the caller's deadline) covering the run and the verification: no count of packets or frames bounds what a decoder does (an AV1 temporal unit or a VP9 superframe carries many frames), so time is the decoder's bound, and the one the provider bills. While ffmpeg runs, a monitor in `core/encode.py`, called through `core/bounded_process.py`'s monitor hook, stops it when the output passes its byte or file allowance (the smaller of the dispatch's output limit and the scratch ceiling less the source). The decoder's refusals of an oversized or invalid frame (libavutil's two size checks, libdav1d's limit) are recognized anywhere in its stderr, not only in the kept tail. ffmpeg can exit 0 without writing a segment, so the output is always verified afterwards: the exact playlist grammar (`core/hls_playlist.py`); every file accounted for, the exact limits, the cut held, and every segment proven whole MPEG-TS (decrypted and its padding checked when encrypted) whose video PTS span matches its EXTINF and whose count of video frames matches that span, in the pass that hashes it (`core/encode.py`); then ffmpeg decodes the whole rendition once through a private copy of its playlist (`-xerror -err_detect explode`), and its decoded frames must equal the frames counted; less than 1 MiB of disk left after the run, or behind a failure, is a retryable `scratch_full`. Known gaps, both advisory (a write failure cannot practically produce them: on the image's ffmpeg 7.1.4, plain segments are written in 256 KiB writes and encrypted ones in 32 KiB writes, and ffmpeg writes nothing after a failed write; re-measure on an ffmpeg upgrade): whole audio packets lost after a segment's last video frame decode clean, so no check sees them (a strict xfail test records it); and on ffmpeg 8.0.1 (arm64) some cuts inside the very last frame decode clean, which 7.1.4 refuses. When the stages are wired (D1), encode the renditions of a job one at a time on a shared scratch disk: a failed sibling's removal could otherwise free the space the free-disk check relies on. The bandwidth is measured from the segments on disk (RFC 8216 4.3.4.2). Tests: `tests/encode/` (the memory-key tests run only on Linux: run the suite in the worker image too).

## Thumbnail, master playlist and manifest (B08 core, D3 of the Hub's issue #51; not wired yet)

`core/thumbnail.py` `make_thumbnail()` writes the optional `thumbnail.jpg`: the picture on screen a tenth into the admitted duration but never later than 5 s (the `fps` filter first, as the renditions have it, and the seek snapped down onto that frame grid, so a still image or a slide show still shows its picture), read through the rendition's own input arguments (`core/encode_command.py` `input_arguments`) and sought on the output side (ffmpeg decodes from the start rather than trust the container's seek index), turned by exactly the admitted rotation, scaled to the largest rendition's aspect at the profile's short edge (never upscaled) and written as a baseline 4:2:0 JPEG holding nothing but its image (an ICC profile travels as frame side data, so the filter chain deletes it; `+bitexact` keeps the encoder's comment out), within its own byte limit and time budget (`EncodeProfile.thumbnail_*`); the file is verified (a regular file within the limit, a whole JPEG whose frame header names the planned size and with no segment before its scan but a JFIF header, its tables and its frame: any metadata segment is refused) before it becomes an artifact. It is optional: every other ending is a `thumbnail_unavailable` diagnostic (`core/failure.py` `Diagnostic`) with no file left, and only the caller's deadline and a full scratch disk fail the job. `core/package.py` writes the master playlist (`#EXTM3U`, version 3, independent segments, then for each rendition in planned order a `STREAM-INF` with the measured `BANDWIDTH` and `AVERAGE-BANDWIDTH`, `RESOLUTION`, `FRAME-RATE` to three decimals and `CODECS`, followed by its playlist path) and, last, the contract v2 `generation.manifest`: compact JSON in the schema's key order listing the master, the thumbnail and every rendition's playlist and segments with size and SHA-256; the manifest is never an artifact itself, and its preconditions fail only on a wiring bug. Both files are created new (`O_EXCL`, `O_NOFOLLOW`); a failed write removes the partial file and is typed (`scratch_full` or `package_write_failed`). The job calls `reserve_package()` right after `OutputAllowance.for_job()`: it sets aside the master's 4 KiB, the thumbnail's `thumbnail_max_bytes`, the manifest's `manifest_max_bytes(max_artifacts)` and two files, and gives the renditions the rest. D1 wires the stages; the worker_sender self-check with the contract validator runs once the validator moves into `core/`. Tests: `tests/encode/test_thumbnail.py`, `test_package.py` (the manifest passes the contract validator, its worst case included) and `test_package_end_to_end.py`.

## Webhook Contract

POST /transcode with JSON body (see core/api.py for schema). Auth: HMAC-SHA256 over `"{timestamp}.{raw_body}"` with the shared `WEBHOOK_SECRET` — headers `X-Signature: sha256=<hex>` + `X-Timestamp: <epoch>` (5-min tolerance). The RunPod wrapper skips inbound HMAC (RunPod API key gates dispatch) but still signs outbound callbacks.

`_process_transcode` returns the result payload (status `ready`|`failed`); callback delivery is attempted but non-fatal. The RunPod handler returns that payload as the job output (and raises on failure so RunPod marks the job FAILED) — Video Hub polls job status as the reliable path.

## Key Conventions

- Video ID: UUID v4
- Quality presets match Video Hub's TranscoderService.php exactly
- Encryption: AES-128, key provided as hex in request, written to temp file for FFmpeg
- R2 upload skips .keyinfo and enc.key files (keys served from Video Hub DB)
